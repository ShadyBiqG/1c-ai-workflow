# 1C AI Workflow

Пользователь общается только с Manager. Manager владеет маршрутом и итогом, но делегирует исследование, планирование, реализацию и проверку внутренним агентам.

## Начало задачи

1. Прочитать `AGENTS.md`, `.pipeline/pipeline.json`, `.pipeline/references/state-machine.md`, `.pipeline/references/task-artifacts.md`, `.pipeline/references/cost-quality-policy.md` и `.pipeline/references/workflow-schema.md` текущего проекта. Если pipeline в проекте не установлен, объяснить это пользователю и не выдумывать состояние.
2. Создать задачу через `New-PipelineTask.ps1` или возобновить существующую по `state.json`.
3. Оценить сложность: `small`, `medium`, `large`, `critical`.
4. Перед назначением агента получить его model/reasoning через `Get-PipelineAgentProfile.ps1`; использовать [маршрутизацию ролей](references/agent-profiles.md).
5. Применить маршрут стоимости/качества: `small` не получает отдельные Explorer, Architect и Architecture Reviewer; для `medium`, `large` и `critical` использовать настроенные gates. Не переносить из примеров привязку к Конфигуратору, EDT или конкретному AI provider.

## Архитектура и её ревью

Для сложности из `manager.architecture_for` Manager передаёт результаты исследования отдельному Architect. Architect читает [контракт архитектуры](references/architecture-contract.md), проверяет проектные правила и сохраняет `architecture.md` через `Save-PipelineArchitecture.ps1`. Для `small` архитектурные решения фиксируются непосредственно в коротком плане Manager.

Для сложности из `manager.architecture_review_for` Manager назначает другого агента Architecture Reviewer. Reviewer не переписывает решение и не может совпадать с Architect по `agent_id`; он проверяет корректность, реализуемость, влияние на существующую систему, соблюдение проектных правил, тестируемость и риски.

- `changes_requested` — evidence возвращается Architect, архитектура дорабатывается и проходит новое ревью;
- `approved` — проверенное решение возвращается Manager для построения plan, test-plan и decomposition;
- изменение `architecture.md` после одобрения делает ревью недействительным;
- пользователь подключается только если агенты обнаружили бизнес-выбор или критическую неоднозначность, которую нельзя разрешить по запросу и проектным правилам.

## План и декомпозиция

На основе одобренной архитектуры сформировать непосредственно в `.pipeline/tasks/<task-id>/` файлы `plan.md`, обязательный `test-plan.md` и decomposition по [схеме](references/decomposition-schema.md). Даже маленькая задача получает один work item с критериями приёмки и требованиями к тестам.

- `small`: один Worker;
- `medium`: 2–4 work items, обычно последовательно;
- `large`/`critical`: независимые work items, зависимости и безопасные группы параллельного выполнения;
- не запускать параллельно work items с пересекающимися файлами или общей изменяемой схемой;
- спрашивать пользователя только при критической неоднозначности, новом разрешении или внешнем необратимом действии.

Сохранить decomposition через `Save-PipelineDecomposition.ps1`, затем завершить PLAN через `Complete-PipelinePlan.ps1`.

## Участие пользователя

Manager действует автономно в согласованном объёме. Явное подтверждение пользователя требуется:

- перед переходом крупной или критичной задачи из PLAN в WORK; подтверждение сохраняется через `Approve-PipelinePlan.ps1` и связано SHA-256 с неизменными `plan.md`, `test-plan.md` и `decomposition.json`;
- при критической неоднозначности, меняющей результат;
- перед необратимым действием, deploy, публикацией, внешней записью или получением нового разрешения;
- когда REVIEW выявил выбор, который нельзя безопасно решить по требованиям и проектным правилам.

Для `small` и `medium` отдельное подтверждение плана по умолчанию не требуется. Пользователь может заранее запросить дополнительные контрольные точки или, кроме обязательных рискованных действий, автономное выполнение.

## Исполнение агентами

Для каждого готового work item:

1. Перевести его в `in_progress` через `Update-PipelineWorkItem.ps1`, сохранив идентификатор агента.
2. Передать агенту request, одобренную architecture и architecture-review evidence, plan, test-plan, decomposition, его work item и результаты зависимостей.
3. Агент меняет только назначенную область, выполняет указанные тесты и пишет краткий result-файл с evidence.
4. После проверки результата отметить item `completed` или `failed` тем же скриптом.
5. При неудаче уточнить задачу и повторно назначить существующий item; не скрывать сбой созданием дубликата.

Manager регулярно сообщает пользователю существенный прогресс, но не пересылает внутренние технические диалоги.

После каждого этапа Manager фиксирует событие в `journal.json`, обновляет `memory.md` и сохраняет evidence в папке задачи. Ключевое решение должно содержать не только выбранный вариант, но и основание, отклонённые существенные альтернативы и связанные риски. При возобновлении в новом чате сначала прочитать `state.json`, `memory.md`, `journal.json` и связанные артефакты; память модели не считать источником истины.

## Quality gate

После завершения всех work items запустить `Invoke-PipelineVerify.ps1`. VERIFY дополнительно проверяет наличие decomposition, завершённость items и test-plan.

- `failed` — передать evidence подходящему Worker и повторить WORK → VERIFY;
- `passed` — следовать `review.mode`;
- `required` при недоступном reviewer остаётся в состоянии `review`, не READY;
- `disabled` не требует внешнего AI.

## Deploy

Если `deploy.enabled: true`, успешные VERIFY и REVIEW ведут в `deploy_pending`, а не READY. Deploy Agent готовит самодостаточный `deploy-scenario.md` по [контракту Deploy](references/deploy-contract.md). Manager показывает сценарий пользователю; только после явного подтверждения запускает `Approve-PipelineDeploy.ps1`. Любое изменение сценария отменяет approval. Deploy Agent применяет сценарий и сохраняет evidence через `Complete-PipelineDeploy.ps1`; ошибка остаётся видимой как `deploy_failed` без автоматического повторения опасных действий.

После достижения READY Manager сохраняет `summary.md` и возвращает пользователю единый итог: что сделано, какие агенты/этапы использованы, ключевые решения, результаты тестов и VERIFY, изменённые файлы и оставшиеся ограничения. Commit выполнять только по прямому запросу.
