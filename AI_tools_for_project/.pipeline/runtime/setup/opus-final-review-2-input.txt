     finally {

             Remove-Item -LiteralPath $tempPath -Force

     C2 --> CE

-Только Manager маршрутизирует переходы. Plan, Work и Deploy возвращают результат Manager и не запускают друг друга напрямую. Детерминированный boundary-controller выполняет только транспорт, ожидание idle и компактизацию; он не принимает инженерных решений и не является пятой ролью.
+Только Manager маршрутизирует продуктовые переходы. Plan, Work и Deploy возвращают результат Manager и не запускают друг друга напрямую. Вызывающий проектный чат выполняет только двухфазное обслуживание boundary: App archive/restore, запуск compaction transport и проверку project snapshot. Он не принимает инженерных решений и не является пятой долговременной ролью.
 
 Для обычных переходов Manager использует операции Codex task transport: отправляет follow-up в зарегистрированный thread и ожидает его завершения. Финальный ответ роли автоматически становится входом Manager; пользователь не должен вручную переносить сообщения между чатами.
 
 ## 5. Жизненный цикл задачи
 
 ### 5.1 Intake и граница контекста
 
-1. Пользователь отправляет новую задачу в Manager.
+1. Пользователь отправляет новую задачу Manager через вызывающий чат этого проекта.
 2. Manager создает уникальный `task ID` и сохраняет исходный запрос в `.pipeline/tasks/<task-id>/request.md`.
-3. Manager запускает boundary-controller и завершает intake-turn без планирования.
-4. Controller ждет, пока Manager и остальные задачи станут idle.
-5. Controller компактизирует Manager, Plan, Work, Deploy и единую Opus-сессию.
-6. Только после пяти подтвержденных результатов controller запускает новый turn Manager с коротким `TASK_READY`, task ID и путями к request/receipts.
+3. Manager возвращает `BOUNDARY_REQUIRED <task-id>` и завершает intake-turn без планирования.
+4. Вызывающий controller архивирует четыре роли через Codex App, освобождая Desktop writer-lock.
+5. Phase-one helper временно CLI-unarchive каждую роль, получает `contextCompaction`, затем снова CLI-archive тот же ID.
+6. Controller разархивирует роли через Codex App и проверяет исходные `project_id`, ID и названия, а также `pinned=false`.
+7. Completion script компактизирует единую Opus-сессию и собирает пять receipts.
+8. Completion сохраняет точный текст и hash `TASK_READY` и переводит задачу в `task_ready_pending`.
+9. Controller запускает новый turn Manager с этим текстом, ждет completion, отдельно читает Manager через Codex App и сохраняет task-scoped read receipt. Скрипт подтверждения проверяет в нем точный текст, thread ID и completed turn; только затем состояние становится `plan_requested`.
 
 Таким образом, сам исходный запрос не теряется при компактизации Manager, но содержательная работа начинается уже после нее.
 
 ### 5.2 Планирование
 
 1. Manager передает в ту же задачу Plan task ID, достаточный контекст и ссылки на артефакты.
 2. Plan исследует конфигурацию read-only навыками 1С и строит draft.
 3. Plan автоматически отправляет draft в ту же Opus-сессию.
 4. Plan разбирает каждое существенное замечание Opus, фиксируя статус `accepted` или `rejected` с обоснованием.
 5. Plan создает `.pipeline/tasks/<task-id>/plan.md`, коммитит план и возвращает Manager commit hash и путь.
 6. Manager не проверяет полноту плана и не создает плановый commit. Он владеет только фактом существования плана и следующим переходом.
 
 ### 5.3 Реализация и review loop
 
 1. Manager отправляет Work task ID, plan path/commit и необходимый контекст, выбранный по материалам Plan.
 2. Work реализует план, обязательно выбирает применимые навыки 1С, тестирует и коммитит результат.
 3. Manager отправляет итог в ту же задачу Plan. Сам план повторно не пересылается: Plan сохраняет контекст и имеет файл плана.
 4. Plan делает review, автоматически получает второе мнение той же Opus-сессии и публикует единый verdict.
 5. При `changes_requested` Manager возвращает verdict в ту же задачу Work.
 6. Цикл повторяется без лимита и без эскалации пользователю, пока замечания не закончатся.
 7. Только `approved` разрешает Manager перейти к Deploy.
 
 ### 5.4 Deploy и human gate
 
 1. Deploy читает утвержденный план, review verdict и evidence Worker.
 2. Deploy выполняет только read-only dry-run и возвращает Manager полный сценарий: база, команды, ожидаемые записи/изменения, проверки, условия остановки и восстановление.
 3. Manager показывает сценарий пользователю и один раз получает явное одобрение или отказ.
 4. Manager передает Deploy approval artifact, привязанный к hash сценария. Одно одобрение разрешает все записи и шаги, явно входящие в этот сценарий, включая множественные записи теста. Новая операция вне сценария требует нового одобрения.
 5. Deploy проверяет hash, применяет изменения, выполняет сценарные проверки и сохраняет полный evidence.
 
 ## 6. Протокол compaction
 
 ### 6.1 Codex
 
 Controller использует официальный Codex App Server по JSONL/stdin:
 
 1. `thread/resume` для зарегистрированного thread ID;
 2. проверка, что thread idle и ID соответствует реестру;
 3. `thread/compact/start`;
 4. ожидание `contextCompaction` lifecycle до `item/completed`;
 5. запись receipt с thread ID, временем, статусом и идентификатором события.
 
-Большие JSON и инструкции не передаются аргументами процесса. App Server получает их через UTF-8 stdin. Controller компактизирует задачи последовательно, чтобы исключить конкуренцию за общий checkout и локальное хранилище Codex.
+Большие JSON и инструкции не передаются аргументами процесса. App Server получает их через UTF-8 stdin. Controller компактизирует задачи последовательно, чтобы исключить конкуренцию за общий checkout и локальное хранилище Codex. В Codex Desktop отдельный App Server не может resume задачу с активным writer-lock, поэтому App archive/CLI compact/App restore является частью протокола. CLI-unarchive не считается восстановлением проекта.
 
 Codex compaction не принимает focus-инструкцию. Поэтому долговечные правила живут в `AGENTS.md` и role-contract файлах, а факты задач - в `.pipeline/tasks`. После сжатия первая короткая команда роли требует перечитать ее contract и текущий envelope.
 
 ### 6.2 Claude Code
 
 Claude wrapper возобновляет зарегистрированную сессию и отправляет через UTF-8 stdin:
 
 ```text
 /compact Preserve the pipeline role, UT configuration identity, cross-task decisions,
 known constraints, and reusable lessons. Drop completed-task details, raw diffs,
 raw logs, duplicate file contents, and transient tool output.
 ```
 
 Успех подтверждается SDK-событием `system/compact_boundary`; receipt хранит `session_id`, trigger и доступное значение `pre_tokens`. Project-root `CLAUDE.md` содержит раздел `Compact Instructions` и повторно загружается Claude Code после compaction.
 
 ### 6.3 Атомарность границы
 
 - Новая задача не отправляется Plan до завершения всех пяти compaction.
-- Повторный запуск boundary-controller идемпотентен: существующий успешный receipt не выполняется заново без флага `-Force`.
-- Ошибка compaction блокирует старт задачи, но не создает новую сессию.
+- Повторный запуск boundary-controller идемпотентен: phase-one хранит receipt каждой роли отдельно и пропускает уже подтвержденную работу; успешные Codex/Opus receipts и pending `TASK_READY` не выполняются заново без флага `-Force`.
+- Ошибка compaction переводит задачу в `blocked`, но не создает новую сессию. Явно разрешенное восстановление оставляет audit artifact и возвращает `blocked -> compacting`, продолжая с отсутствующего receipt.
+- Project snapshot содержит `task_id` и `captured_at`, обязан быть новее завершения phase-one и явно подтверждать `project_id`, `pinned=false`, `archived=false` для каждой роли.
 - Автоматическая замена отсутствующей сессии запрещена. Manager сообщает пользователю конкретный ID и просит прямое разрешение на создание новой.
 - Raw stdout/stderr и JSON events пишутся в `.pipeline/runtime/<task-id>/` и не коммитятся; нормализованные receipts и итоговые evidence хранятся в `.pipeline/tasks/<task-id>/`.
 
 ## 7. Windows transport
 
 Для Codex App Server и Claude Code применяются одинаковые правила:
 
 - исполняемый файл и короткие валидированные флаги допустимы в command line;
 - prompt, plan, review, diff, schema и большие JSON передаются только файлами или UTF-8 stdin;
 - stdout/stderr перенаправляются в файлы, затем разбираются структурированным JSON parser;
 - внешний wrapper совместим с Windows PowerShell 5.1 и запускает bundled Node transport через `System.Diagnostics.ProcessStartInfo`;
 - PowerShell передает Node только пути к временным UTF-8 config/result файлам; Node пишет чистый UTF-8 без BOM напрямую в stdin Codex/Claude;
 - прямой `Process.StandardInput` из Windows PowerShell 5.1 не используется: .NET Framework добавляет BOM `U+FEFF`, а свойства `StandardInputEncoding` в этом runtime нет;
 - background helper запускается скрыто (`-WindowStyle Hidden`) и пишет heartbeat/state в runtime-каталог;
 - пути передаются как отдельные аргументы без ручной конкатенации shell-команд;
 - секреты не передаются через command line и не записываются в committed artifacts.
 
 Claude wrapper ищет максимальную semver-версию в `%APPDATA%\Claude\claude-code\<version>\claude.exe`, затем проверяет документированные fallback-пути. Обнаруженная сейчас версия: `2.1.222`; жестко фиксировать этот номер нельзя.

 ## 9. Границы навыков 1С
 
 ### Manager
 
 Не меняет исходники и базу, не вызывает инженерные навыки 1С и не запрашивает второе мнение Opus. Разрешены только чтение pipeline-state, Git metadata и транспортные операции.
 
 ### Plan / Reviewer
 
 Разрешены аналитические read-only навыки по необходимости:
 
 - `cf-info`, `cfe-diff`, `meta-info`, `form-info`, `form-patterns`;
 - `subsystem-info`, `role-info`, `skd-info`, `mxl-info`, `xdto-info`;
 - `web-info`, `db-list`, `img-grid`;
 - `meta-decompile`, `form-decompile`, `skd-decompile`, `mxl-decompile`, `xdto-decompile`, если без них нельзя построить или проверить план.
 
 Запрещены edit/compile/remove/load/update/publish операции и любые записи в информационную базу.
 
 ### Work
 
 Для каждой 1С-задачи обязан выбрать профильную цепочку:
 
 ```text
 info/decompile -> edit/compile/add/remove -> matching validate -> tests
 ```
 
 Разрешены навыки редактирования конфигурации/расширения, метаданных, форм, подсистем, интерфейса, ролей, СКД, MXL, XDTO, EPF/ERF, макетов и справки. `support-edit` используется только если это явно предусмотрено утвержденным планом. Work не загружает изменения в рабочую информационную базу и не выполняет deploy-команды.
 
 ### Deploy
 
 Не редактирует исходники. Разрешены `db-list`, `db-load-git`, `db-update`, `db-run`, согласованные backup skills, валидаторы и навыки `web-*` в пределах утвержденного сценария. Любая операция записи возможна только после human gate.
 
 ## 10. Цепи Superpowers
 
 Все роли начинают с `superpowers:using-superpowers`.
 
 | Роль | Обязательная/типичная цепочка |
 |---|---|
 | Plan | `brainstorming` -> аналитические 1С skills -> `writing-plans` -> Opus second opinion -> commit |
 | Work | `executing-plans` -> `test-driven-development` -> профильные 1С skills -> `systematic-debugging` при сбое -> `verification-before-completion` |
 | Work после замечаний | `receiving-code-review` -> исправления и тесты -> `verification-before-completion` |
 | Plan review | аналитические 1С skills -> Opus second opinion -> единый verdict |
 | Deploy | `executing-plans` -> dry-run -> human gate -> 1С deploy skills -> `verification-before-completion` |
 | Создание pipeline skills | `skill-creator` + `superpowers:writing-skills` + TDD pressure tests + validation |
 
 `dispatching-parallel-agents` не применяется для ролей, пишущих в общий checkout. Параллельность допустима только для независимых read-only исследований, если она не нарушает правило sole-router.
 
 ## 11. Планируемые проектные skills
 
 ### `onec-pipeline`
 
 Оркестрация Manager: task ID, envelopes, state machine, Codex task registry, ожидание результатов, review loop, deploy gate и boundary-controller.
 
 ### `claude-consilium`
 
 Безопасный вызов Claude Code из любой разрешенной задачи и при разных моделях вызывающего Codex-чата: `start`, `ask`, `compact`, `status`. Начальный профиль `opus/high`, одна сессия, stdin/file transport, JSON receipts. В начальной role policy Plan имеет право на `ask`, controller - только на `compact/status`; расширение матрицы не потребует переписывать transport skill.
 
 Оба skill создаются через `skill-creator`, получают `agents/openai.yaml`, минимальный `SKILL.md`, references/scripts и проходят `quick_validate.py` плюс pressure-тесты.
 
 ## 12. Git и владение commit
 
 - До pipeline создается baseline commit всей текущей конфигурации.
 - Plan коммитит только plan artifacts.
 - Work коммитит реализацию и тесты.
 - Plan review не переписывает commit Worker; verdict фиксируется отдельным artifact/commit при необходимости.
 - Deploy не редактирует исходники и не создает фиктивный implementation commit.
 - Manager не делает плановый commit и не исправляет содержимое чужих артефактов.
 - Перед началом каждого пишущего этапа проверяется чистота ожидаемой части working tree. Неизвестные пользовательские изменения не откатываются.
 
 ## 13. Надежность и восстановление
 
 - Каждый переход идемпотентен по `correlation_id`.
 - Manager хранит state machine на диске и после resume сверяет ее с Git и task artifacts.
 - Таймаут ожидания не означает неуспех задачи: Manager повторно читает состояние той же задачи.
 - Потеря/архивация role thread или Opus session останавливает pipeline до прямого решения пользователя.
 - Review loop не имеет счетчика неудач и никогда не создает новый Plan/Work thread.
 - Ошибка сценария Deploy останавливает оставшуюся часть сценария, сохраняет evidence и возвращается Manager. Она не разрешает скрытые повторные записи.
 - Одобрение deploy привязано к hash текста сценария; изменение сценария делает старое одобрение недействительным.
 
 ## 14. Проверка реализации
 
 До использования на реальной задаче должны пройти следующие проверки:
 
 1. Созданы ровно четыре Codex-задачи с заданными моделями/effort, названиями и сохраненными ID.
 2. Повторный setup переиспользует ID и не создает новые задачи.
 3. Codex App Server компактизирует каждую idle-задачу; получено `contextCompaction/item/completed`.
-4. Boundary-controller способен компактизировать сам Manager после завершения intake-turn и возобновить его через `TASK_READY`.
+4. Двухфазный controller способен компактизировать сам Manager после завершения intake-turn, вернуть все роли в исходный saved project и возобновить Manager через `TASK_READY`.
 5. Claude Code создает одну Opus-сессию, возобновляет ее по ID и подтверждает `/compact` событием `compact_boundary`.
 6. Русский текст проходит через оба wrapper без `?`, mojibake и потери перевода строк.
 7. В command line отсутствуют plan/review/prompt/schema; они видны только в stdin или файлах.
 8. Plan автоматически вызывает Opus для draft plan и review, а accepted/rejected замечания отражены в artifacts.
 9. Work отклоняет 1С-задачу без выбранного профильного skill и matching validation.
 10. `changes_requested` возвращается в тот же Work без лимита; `approved` переводит в тот же Deploy.
 11. Deploy до gate выполняет только read-only dry-run.
 12. Одно одобрение hash-фиксированного сценария разрешает несколько предусмотренных записей; изменение сценария снова закрывает gate.
 13. Негативные тесты: отсутствующий thread ID, занятый thread, битый session ID, не найденный Claude CLI, невалидные model/effort, невалидный JSON, timeout, повторный correlation ID.
 14. Все новые skills проходят `quick_validate.py`, а PowerShell scripts - syntax check и интеграционные тесты на Windows PowerShell 5.1.
